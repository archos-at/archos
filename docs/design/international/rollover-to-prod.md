# Rolling country knowledge over from dev to prod

Read at `origin/develop` `ed5d4e4b2e` and `origin/prod` `f48bdcc4cd` (2026-11-11). Prod runs `sha-331b9d9117661b201c762a7017f9c0d17ec21866` (the `prod` branch's `deploy/pulumi/Pulumi.prod.yaml`, 2026-10-28), migrations through `0191`. Dev holds Austria (`5907f5cb-…`, 312 records, 408 revisions, 50 texts) and the EU (`c323cdc4-…`, 5 records), both `submitted`, neither published. Nothing here was run against prod.

## The answer

The only point where prod would answer worse than today is the time between the code promotion and Austria's stable publish on prod. In that window every Austrian office's turn has gate `none` (or `site_unknown`). It still reads the corpus and RIS, but it names no binding edition, derives no building class, and caps any answer that cites building law at medium (finding 1). The sequence below keeps that window as short as possible: everything that can happen before the promotion happens before it, and the prod review checks identity with the reviewed dev release instead of starting over. Removing the window entirely would take a release with the old answer path and the new door, and develop has no such commit (finding 1, last paragraph). That decision is the owner's (open question 1).

**The rule for develop.** Prod promotes everything that has merged up to the sha it pins. So a PR that deletes an old path, or that makes an answer depend on published records it did not depend on before, merges only after prod has those records on `stable` (step 8). Until then, a deletion PR waits even when dev is green. The same holds for every later country path: the records come first on every environment the next promotion reaches, and the code that needs them comes after.

## Findings

### 1. A prod office the moment prod runs today's develop with nothing published

- **Placement and entitlement are data, and every existing office gets AT.** Migration `0200_organization_home_country.sql:58-83` inserts a row for every organization that owns any tenant row and sets `home_country = 'AT'` and `time_zone = 'Europe/Vienna'` wherever it is NULL. `knowledge_country_entitled` counts the home country (`0205_platform_base_knowledge.sql:393-398`) and adds `EU` through the territory parents (`0219_territory_parents.sql:39-46`). No WorkOS switch is involved. An organization created in the WorkOS dashboard after the promotion gets its row on its first page load, and gets a country only if its WorkOS metadata names `home_country` (`bff/organizations/home-country-row.ts:1-20`). Without one its gate is `organization_unplaced`: no corpus and no RIS (`knowledge_context.py:48`).
- **Gate.** `resolveKnowledgeContext` (`bff/base-knowledge/context/resolve.ts:247-276`) gives a project in Austria `none` (no released territory carries coverage, so `coverageAt` finds none), a project with no site `site_unknown`, and a site outside AT `not_entitled`. `knowledge_unavailable` comes only from a graph read that fails or hits its safety bound (`MAX_ROWS` in `chain/load.ts`; no count of uses withholds law since plan row 5). With no records the graph is empty, so the bound is not hit, but any failed read withholds all law for that turn, by design. `none` and `site_unknown` read law (`reads_law`) and bind nothing (`may_bind` false), and are not settled (`knowledge_context.py:47-56`).
- **Base-corpus retrieval.** Every vector read goes through `corpus_country_condition` (`vector_store/scope.py:250-284`): a corpus chunk passes only if its `country_id` is in the request's countries. Those are the turn's `retrieval.countries`, which are `[AT]` for an Austrian site (`resolve.ts:241-244`, `:264`) and the entitled set (`[AT]`) without a site (`:251`). A chunk without `country_id` passes nothing.
- **The legacy backfill does run on prod, at the first sync after the deploy.** `oib_sync.sync` calls `backfill_legacy_marks` first, under the sync lock (`oib_sync.py:500-509`). It marks every corpus file that has no mark row as `AT`, in the vector store and in the table, records a marker row, and never runs again (`oib_sync.py:470-497`, `corpus_store.py:316-340`). The sync runs from the CronJob `housekeeping-base-corpus` every 10 minutes (`deploy/pulumi/src/app/workers.ts:302-308`), which is suspended only while `chromaMigration` is on. Prod's config says never to set it again (`Pulumi.prod.yaml:278`). The operator's `platform-knowledge-sync` runs the same function with the marker (`apps/agent-host/src/agent_host/routes/oib.py:110-115`). **Until that first cycle, which takes up to 10 minutes, no office reads any base-corpus chunk.** Step 5 closes that gap by running the sync at once. Dev rehearses this differently: `Pulumi.dev.yaml:151` still has `chromaMigration: "true"`, so on dev the CronJob is suspended and only a manual sync ran the backfill. After the backfill, any file uploaded through the old admin path without a release is stamped `ZZ` and read by nobody (`vector_store/writes.py:125-128`). Upload base-corpus files only through a change request from then on.
- **Office corpus listing and PDF reads (#1621).** The office list and the PDF route show only files whose release mark names one of the office's countries (`bff/knowledge/released-corpus.ts`, `corpus_store.released_to`, `corpus_store.py:349-353`). An unmarked row is nobody's, and so is `ZZ`. Before the backfill, the office's base-corpus page is empty and a cited PDF answers 404. After it, every legacy file is listed for AT offices, as it is today.
- **Law lookup.** `ris-adapter` is still the path: `LAW_SOURCE_COUNTRIES = {"ris": "AT"}` (`common/law_gate.py:30`), allowed wherever the gate reads law and `AT` is in the retrieval countries (`knowledge_context.py:497-507`). With gate `none` or `site_unknown` for an AT office, RIS runs. With `organization_unplaced`, `not_entitled` or `knowledge_unavailable`, it is withheld with a notice (`law_gate.py:47-66`).
- **Setup and building class.** The intake wizard still reads the three Austrian seeds compiled into the build (`bff/base-knowledge/rulesets/shipped.ts:25-29`, `project-intake/setup-scope.ts:75`), so setup facts and the Land question work with no records. The classification, though, refuses on every gate in `REFUSING`, and that set includes `none` (`bff/base-knowledge/wire/project-law.ts:32-35`, `project-intake/classification.ts:173-176`): **no Gebäudeklasse is derived on prod until AT is stable.** Today's prod derives it with the `oib/building-class` skill.
- **Citations.** A role comes only from the turn's `uses`, by edition id, or by a legacy file's name when the records list it (`citations/roles.py:1-40`). Gate `none` carries no uses (`resolve.ts:276`), so no citation shows a binding chip. Any answer citing building law is capped at medium (`law_gate.py:69-82`, `binding_claims.py:12-20`). Today's prod still runs the host-regex binding guesses that R1 deleted.
- **Verdict.** Prod answers get worse for every office placed in Austria, on project questions, from the promotion until AT is stable. The answers stay correct where they quote the corpus or RIS. What drops is the edition named as binding, the derived building class and the confidence level. For about 10 minutes they also lose the base corpus entirely, unless step 5's sync runs. After AT is stable, the dev acceptance says they are better than today (A1, A2, A6, A8). No commit on develop keeps the old answer path behind a switch and also accepts the AT request as built: the last one with switches, `b3fa243d73` (parent of the R2 cut-over `f2bf338cb2`, migrations through 0213), lacks `text-import`, PDF sources (0215), the database four-eyes rules (0218) and text four-eyes (0224), all of which the AT request uses.
- **Duplicates after stable.** Dev imported the OIB texts as new files named `<manifestationKey>-<12 hex>.pdf` (`platform-knowledge-text-list` on dev). On prod the legacy OIB PDFs, now marked AT, stay readable beside them. The legacy copies carry no `knowledge_edition_id`, so a passage read from one gets no role unless the records list its file name. That is what makes a rollback safe. It also means duplicate hits until the legacy copies are retired (open question 2).

### 2. Migrations prod runs, and whether each is safe on its data

Prod's journal ends at `0191_brand_free_policies`. Develop adds `0192` to `0227`. Every one of them has a `when` later than prod's last (both journals compared), so `drizzle-kit migrate` (the migration Job) applies all 36 in order. They are, by kind:

- **New tables and functions only** (empty on prod, nothing to violate): 0192, 0196 (inbound mail), 0202 to 0216, 0220 to 0221, 0224, 0225. The CHECK constraints in these are on tables they create, or on knowledge tables that are empty on prod.
- **Data updates on existing rows:** `0200` places every organization in AT (above). `0201` gives an existing project with an address but no country and no Land the Land of its postcode, as an unconfirmed assumption, and is idempotent (`0201_postal_code_land_backfill.sql:1-27`). `0227` lowers `attempts` from 10 or more to 9 on pending `deletion_queue` rows so that its new constraint holds. The constraint is `NOT VALID`. `0197`, `0214`, `0217` and `0219` update tables that are empty on prod (`inbound_mails` from 0196, knowledge tables from 0202 on).
- **Constraints on existing tables:** `0193`, `0195`, `0200` (`organizations_home_country_iso`, `organizations_time_zone_shape`, both NULL-tolerant and run after the backfill in the same migration), `0203` (NULL-tolerant), `0222`, `0223` and `0227` (`NOT VALID`, so existing rows are not checked). `0194` adds `release_summary_notice boolean NOT NULL DEFAULT true`, which needs no backfill.
- **Drops:** `0226` drops `jobs`, `job_runs` and `tasks`. Checked against prod's image: `bff/jobs/repository.ts` `findJob` is the last reader, and it has no caller there. `bff_job_lane_turns` stays because prod's claim SQL still joins it (`0226_drop_dead_scheduler_schema.sql:27-36`). A rollback to `sha-331b9d9…` therefore runs on the new schema.

None needs a `migration:contract` label (rollback.md). The one real effect a person sees is 0200: offices with no country are now placed in AT, which on prod is every office.

### 3. What prod needs that is not code

- **Entitlements are our data, not WorkOS.** They are `organizations.home_country` plus `organization_countries` rows, read through `knowledge_country_entitled` (`bff/base-knowledge/platform/entitlements.ts:1-10`, migration 0205). 0200 covers existing offices. For a new office, either its WorkOS metadata names `home_country` or an operator places it (`platform-org-countries-list`, home-country move on the person's yes).
- **Permissions and roles.** The authz catalog Job (`grid-app-authz-catalog`, every deploy) creates `platform:knowledge:write`, `:review`, `:approve_as_domain_expert|counsel|privacy_reviewer` and `:approve_alone` (`bff/authz/catalog.ts:249-259`). Who holds them is a WorkOS role assignment on the platform organization. `org-platform-owner` holds all of them (`docs/deployment/workos-provisioning.md:255-257`). Prod needs two people: one who imports (`write`) and one who reviews and approves as domain expert (`review` plus `approve_as_domain_expert`). The reviewer must not hold only `org-platform-owner` in order to approve alone.
- **There is no dev-only review switch in code.** Searched across `apps/workspace/bff`, `app`, `deploy/pulumi/src` and `packages/agent/src`. Single approval is the `platform:knowledge:approve_alone` permission (ADR-0176), and it leaves `approval: single` and a due second review on the request and its releases. For prod the rule is procedural: never use it for the AT and EU import.
- **Feature flags** (WorkOS, must exist in the prod environment or they are off for everybody: `feature-flags.ts:49-51`): `platform-agent-mcp` for the platform door, plus the kept ones `site-resolution`, `source-monitors`, `licensed-seam` (`feature-flags.ts:300-332`). The switches `knowledge-context`, `building-law-chain`, `time-editions`, `platform-base-knowledge` and `office-base-knowledge` are gone from code (`workos-provisioning.md:600-604`).
- **Environment and stack config.** The platform MCP gateway (`mcpGatewayEnabled`, `mcpGatewayPlatformOrgId`, and `PLATFORM_MCP_ADMISSION_TOKEN` derived by `deploy/pulumi/src/platform/mcp-gateway.ts:146-187`) is in develop's `Pulumi.prod.yaml:607-608`. The `prod` branch's copy does not have it yet, and the promotion PR brings it. Hatchet comes with this release (step 4). `geocoderUrl` is needed for address search (`build-split.md`, step 1).
- **Langfuse.** Run `task langfuse:provision` (check) against prod's project. With `-- --apply`, on the owner's yes, it creates the score configs the release adds, among them `binding-claim-without-records` and `law-cited-from-web` (`observability/law_source_scores.py:14-24`).
- **A trap in develop's copy of `Pulumi.prod.yaml`.** It pins `sha-9150f95d…` (2026-09-18), older than what prod runs (`sha-331b9d91…` on the `prod` branch). The promotion PR has to set the tag. If it merged develop's line unchanged, it would roll prod back to September.

### 4. How Austria's and the EU's records get from dev to prod

**What exists.** There is no export and no import of a released change request. The platform door's operations are listed in `bff/agent-api/catalog/` (30 `platform-knowledge-*`, none of them an export). `platform-knowledge-pack-export` exists only as a proposal (`country-as-data.md:115`). `change-request-get` returns each revision's claims as path and value, its citations and its capture metadata (URL, sha256, basis), but not a capture's text. A record must cite a capture of its own request (KC-6), so records cannot move without their captures. Golden cases are not records: the record types are work, edition, manifestation, ruleset, territory, authority, relation and source (`0212_country_onboarding_tooling.sql:52-53`). The checks to run are the dev-acceptance scenarios.

**Option A, re-run the onboarding agent on prod.** No code. It costs a second full agent run, and the run is not deterministic: other quotes, other keys or another record count would give prod a release that differs from what dev reviewed and acceptance-tested. The prod reviewer would have to review 312 records from scratch, and the degraded window would last as long as that review.

**Option B, export a published release on dev and import it on prod as a draft (recommended).** One read operation, `platform-knowledge-change-request-export` (platform-scoped, `platform:knowledge:review`). It writes a JSON file with every revision in proposable form (keyed by record id), each capture (basis, URL, sha256, and the text for `operator_supplied` captures only), each manifestation's text by URL, source and sha256, and the release sequence. The import uses only existing operations, driven by the onboarding guide with the file as input: `change-request-create`, then `citation-capture` per URL (a `fetched` capture is re-fetched on prod, and its sha256 is compared with dev's. If the page changed, KC-6 decides whether the quotes still hold. An `operator_supplied` capture is re-pasted from the file and the reviewer checks it), then `text-import` per manifestation with a sha256 check against the file, then `records-propose` in batches of 200, `validate` and `submit`. The prod reviewer checks that the import equals the release that was reviewed and acceptance-tested on dev, plus every capture whose sha256 differs. Size: about 150 to 250 lines in the BFF (service, route, wire), one catalog entry and one exposure entry, and specs. No migration. The import needs no server code. A server-side import operation would be about 300 more lines and is not needed for two requests.

**As built** (`bff/base-knowledge/platform/release-transfer.ts`). The import became a server operation after all, so that it is one reviewed write instead of an agent's long call sequence:

- **Export.** `platform-knowledge-release-export {countryId}` answers a gzipped JSON file, `knowledge-release/1`. It needs `platform:knowledge:review`. The file holds every stable head as the proposal it was published from (keys, not ids), every capture its citations name with its text, each text's file name, URL and sha256, and `requires`, the records of other countries it names.
- **Import.** `platform-knowledge-release-import` takes that file as an upload and needs `platform:knowledge:write`. It writes one new draft and never submits, approves or publishes.
- **Captures.** Every capture arrives as `operator_supplied`, so the prod reviewer source-checks each one (0209/0224). Re-capturing a page through a reviewed source and re-proposing its record removes that check.
- **Texts.** Each manifestation pins the released sha256. The operator attaches the same bytes with `text-import` or `text-upload`; other bytes are refused with `TEXT_NOT_RELEASED`.
- **Order between countries.** A record that names another country's record not on prod's stable is refused with `REFERENCE_NOT_RELEASED`, so the EU goes first.
- **Repeated import.** The same file again answers `unchanged`.
- **Rehearsal.** `release-transfer.integration.spec.ts` rehearses the whole path on two fresh databases with the synthetic XB and XA.
- **Not measured.** AT's file size is unknown. The door carries a file of up to 5 MB, so a larger one goes through the browser.
