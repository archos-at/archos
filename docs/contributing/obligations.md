# Obligations

Repo-wide. Each service guide adds its own. The root [`AGENTS.md`](../../AGENTS.md)
repeats only the rows that review alone catches; a row whose third column names a
check fails loudly without it.

| When you | You must | What fails you |
|---|---|---|
| Write a commit, or open **or rename** a PR | Conventional Commits: `feat` `fix` `docs` `refactor` `perf` `test` `ci` `build` `chore` `revert`. The **PR title** most of all: the PR is squash-merged, so its title is the commit on `develop`. [`CONTRIBUTING.md`](../../CONTRIBUTING.md#commits-and-pr-titles) | The **Conventional PR title** job (`.github/workflows/pr.yml`). Nothing local checks the title |
| Add or change something a person can do (a route, a button, a setting) | Give it an operation in `apps/workspace/bff/agent-api/catalog/` in the same change, or a reason in `NOT_AN_AGENT_CAPABILITY`. Who sees it (an outside agent, our agent, a native tool of our agent's instead, the platform door, or nobody: `withheld`, with category and reason) is its entry in `apps/workspace/bff/agent-api/exposure.config.ts`. [`headless-first.md`](headless-first.md) | `agent-reachability.spec.ts`; the config does not compile without the entry, and `exposure.config.spec.ts` fails a missing reason or a stale `exposure.json` |
| Name anything in code: a file, folder, identifier, type, enum token, test id, route, API or schema field | **English only, domain words included**, and the standard's word before a plain one before any word of ours. German lives in the i18n dictionaries and in domain data. [`naming.md`](naming.md) | `tests/test_english_names.py` (Python) and `apps/workspace/tests/english-names.spec.ts` (UI), a per-file ratchet on identifiers with the stems in `ci/german_stems.json`; review for file names, routes and string tokens |
| Name anything in code or infrastructure, or write anything a person or an agent reads | **No brand in a name, and the name only as copy** (ADR-0149): name it for what it does, and read the product's name from `packages/brand/identity.json` (`PRODUCT_NAME`, `{productName}`, `{{ product_name }}`). [`naming.md`](naming.md#no-brand-in-a-name) | The `brand-names` hook (`scripts/check_brand_names.py`, identifiers) and the `brand-prose` hook (`scripts/check_brand_prose.py`, retired names and a typed-out current name in text), each a ratchet on its `ci/brand_*_baseline.json`, in `task lint:repo` and CI's **Repo checks** job; `tests/test_product_name_parity.py` for the one source <!-- brand-history --> |
| Write source code or a prompt under `apps/` or `packages/` that needs a country's legal database, standards body, host, territory or law | **A country is records, never code** (ADR-0162, ADR-0168, ADR-0169, ADR-0173, ADR-0174): read it from the knowledge context, the pack or a source record, and name the module, route, tool and identifier for what it does, never for RIS, the OIB or a Land. A prompt (a `.j2` template, Markdown under `prompts/`, a built-in `SKILL.md`) is counted whole. What already names one may only shrink; `task baselines:tighten` locks a shrink in. [The burn-down](../architecture/country-extensibility.md#country-in-code-the-burn-down) | The `country-in-code` hook (`scripts/check_country_in_code.py`, a per-file ratchet on `ci/country_in_code_baseline.json` over the tokens in `ci/country_tokens.json`) in `task lint:repo` and CI's **Repo checks** job |
| Write a file or a function | A TypeScript or JavaScript source file stays at or under 600 lines of code, with no baseline; a Python file stays at or under 600 and a Python function at or under 60, and one already over may not grow (a shrink passes, and `task baselines:tighten` locks it in). Imports, comments and docstrings are not counted; generated files, tests, specs, fixtures, migrations and copy are exempt. Split a file into modules named for their jobs, placed where the layout puts their kind. [`code-conventions.md`](code-conventions.md#size-limits) | The `file-size` hook (`scripts/check_file_size.py` against `ci/size_baseline.json`, which refuses a TS/JS entry) in `task lint:repo` and CI's **Repo checks** job |
| Write a spec | Import the code and test what it does. Never read a source file as text to assert on what it says; a structural guard across the tree parses the code (`@/test-utils/source-ast`, `@/test-utils/sql-statements`, `postcss`) and is listed in `ci/ast_guard_specs.txt`. Set the environment with `vi.stubEnv`, never by writing `process.env`. [`code-conventions.md`](code-conventions.md#specs-test-behaviour) | The `spec-source-reads` hook (`scripts/check_spec_source_reads.py`) and the `spec-env-writes` hook (`scripts/check_spec_env_writes.py`) in `task lint:repo` and CI's **Repo checks** job |
| Write a comment or a docstring | Fix the code instead; three lines per file are free for a contract, a dated measurement, a vendor bug link or a legal constraint, and a file over that may not grow. [`code-conventions.md`](code-conventions.md#comments) | The `comments` hook (`scripts/check_comments.py` against `ci/comment_baseline.json`) on the files you commit, and on all of them in CI's **Repo checks** job |
| Keep a legacy name for one release (an old module, header, route or variable) | Mark it with the phrase `drop after release` on its first line, or at the end of the line that holds the old name, followed by the ISO year and week, `YYYY-Www`, of the release that drops it. Once that week has passed, delete the old name and everything that reads it, or move the marker to the release that will drop it. [`naming.md`](naming.md) | The `legacy-expiry` pre-commit hook (`scripts/check_legacy_expiry.py`), which always runs, and CI's **Repo checks** job, which runs every hook with `pre-commit run --all-files` |
| Name a file, in code, copy or a prompt | Call it Dokument, Datei, Fassung or Stand, never a plan: nothing knows a file is a drawing until its Dokumentart says so ([`CONTEXT.md`](../../CONTEXT.md), „Fassung“) | `forbidden-file-words.spec.ts` (UI copy), `packages/agent/tests/test_product_framing.py` (agent prompts); review elsewhere, the website included (`scripts/check_brand_rules.mjs` does not check this word, and its design-system copy says Pläne for drawings) |
| Describe what the product is, in a doc, a prompt or copy | Lead with the workspace for architects; building law is one capability, never the frame ([`VISION.md`](../../VISION.md)) | `packages/agent/tests/test_product_framing.py` on the first-impression docs and every agent prompt; review elsewhere |
| Add an environment variable | Add its row to [`docs/deployment/environment-variables.md`](../deployment/environment-variables.md) in the same change | The `env-docs` pre-commit hook (`scripts/check_env_docs.py`) for the queue-worker files; review elsewhere |
| Change what a customer can notice | `task release:note -- <slug>` | The `release-notes` pre-commit hook, then CI's **Repo checks** job (its release-note step) |
| Change what a customer can **see** | Capture it and attach it to the PR: `agent-browser` to shoot, `before-and-after` to publish. Commit no image files. [`visual-screenshots.md`](../ux/visual-screenshots.md) | Review |
| Add or edit anything under `skills/` | Add a skill only for agent-specific procedure; anything a contributor needs too is a document ([the rule](agent-skills.md#skill-or-document)). Commit the re-locked `apm.lock.yaml` with it (`task agents:audit` rewrites it): `skills/` is the one source, and the generated `.claude/` and `.agents/` are gitignored, so nothing else in your diff shows the lockfile went stale | `task lint:repo` and CI's **Repo checks** job for the lockfile; review for the rule |
| Change behaviour a doc describes | Update the doc in the same commit. An agent acts on a stale doc | Review |
| Add a model call, a quality check, an agent step or a surface | Make it observable in Langfuse (ADR-0089): a model call is a generation (`observed_generation` outside a workflow run), a check is a score declared in `SCORE_DEFINITIONS`, a dimension is trace metadata. [`docs/observability/`](../observability/README.md) | `test_model_calls_are_traced.py`, `test_langfuse_scores.py`, review |
| Change what shapes an answer: the prompt, the card or envelope contract, retrieval, ingestion, the answer pipeline, a model or effort default | Run the AT golden run on dev (`platform-knowledge-golden-run`) before and after the change is deployed there, and put both summaries in the PR or its follow-up. The local `task be:eval:answer-suite` is optional, for a change not yet deployable. [Which run gates a change](testing-and-verification.md#which-run-gates-a-change) | Review. Nothing else sees seconds, cost or a wrong value in a real answer |
| Change a surface listed in `docs/design/lifecycles/` (the chat turn) | Update its rows. [`lifecycle-matrix.md`](lifecycle-matrix.md) | Review |
| Move the default model | Save it in the admin UI (Platform → Models); `configs/` model names are only the boot fallback. [`org-model-configuration.md`](../architecture/org-model-configuration.md) | Review |
| Say a change is done, finished or ready, or open a PR | Clear [`definition-of-done.md`](definition-of-done.md) and put its closing checklist, every line filled with evidence or with why not, in your summary | Review |
| Learn something the repo could have told you, yourself or through a subagent's report | Verify it in the code, then write it where the next agent will already be looking (the area's doc, the scoped `AGENTS.md`, gotchas, the ADR, the glossary), in the same change. Fix a doc-versus-code discrepancy in whichever is wrong. [The case](working-style.md#everything-you-learn-is-written-down), [the ratchet](correction-ratchet.md#human-intervention-is-a-failure-signal) | The **What we learned** line of the [closing checklist](definition-of-done.md#the-closing-checklist); review for whether the list is complete |
| Add a service to the stack | Add it to Compose **and** Pulumi, or say in the PR why only one ([`deploy/README.md`](../../deploy/README.md#rules-for-changes)) | Review. The two paths diverge silently |
| Edit a `Pulumi.<stack>.yaml` | Leave the `secure:` values as they are; set or rotate one only with `pulumi config set --secret` | Nothing. The values are encrypted by the stack's key and committed on purpose |
| Change a Pulumi manifest | Add a case in `deploy/pulumi/index*.spec.ts` | Review. A typecheck proves nothing about a manifest |

`task verify` runs the task definitions CI calls, so a pass is strong evidence,
not a guarantee. Before a push, `task verify:fast` runs what your diff against
`origin/develop` reaches, as CI's Plan job picks it (`-- --all` for every tier).
Four gates sit outside `verify`, because each needs PostgreSQL server binaries
or IfcOpenShell, and are still required:

- `task db:test:rls` when you touch the tenant boundary or the BFF claim queue (CI's **Workspace** job);
- `task be:test:postgres` when you touch a Python claim queue's SQL (CI's **Backend suites** job);
- `task cms:test:db` when you touch `apps/cms` (CI's **CMS** job, through `cms:verify`);
- `task pkg:test` when you touch `packages/ifc-spatial-py` (CI's **Standalone packages** job).
